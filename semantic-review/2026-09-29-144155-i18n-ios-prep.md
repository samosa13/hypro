# i18n infrastructure and iOS install prep for Hypro

Introduces an internationalization layer (`src/i18n/`) with Spanish as the default and only shipped locale, migrates every UI screen from inline Spanish literals to `t('key')` lookups, adds a language selector in Settings that persists `settings.locale`, and wires iOS PWA meta tags into `index.html`. The design goal is to make adding a second language a matter of dropping in a new dictionary and extending `APP.supportedLocales`, without touching screen code. A verification script confirmed all 116 keys referenced via `t()` resolve against the 123 keys in `es.js`, and the 7 i18n unit tests pass.

Watch for: several user-facing strings were **not** migrated and remain hardcoded Spanish (motivation phrases, seed exercise names, progression coach text, the "Cargando…" boot message, and a few fallback/unit literals) — acceptable for a Spanish-only launch but each is a latent bug the day a second language ships (confirmed). The `apple-touch-icon` absolute paths are correct for production but 404 under `npm run dev` (confirmed). The install/update banner order relative to `setLocale` is harmless today but wrong for multi-language (confirmed).

**Verdict**: APPROVED

## High-level view

The translation layer is sound. `t()` does key lookup with a two-step fallback (current locale → Spanish → the raw key), placeholder substitution is regex-based and leaves unmatched `{name}` tokens visible, and `resolveInitialLocale` correctly gates both the saved preference and the browser language through `supportedLocales`. There are no broken keys: every static `t('...')` and the one dynamic `t(\`lang.${code}\`)` resolves. The stale-locale question resolves cleanly — a saved `locale` no longer in `supportedLocales` is ignored and the app falls back to browser/default, so no crash and no raw keys.

The `t` naming collision in `main.js` is properly fixed. The two loops that previously bound `t` as the iteration variable now use `tab` and `x`, so the imported `t()` is in scope where the tab label is rendered (`t(tab.labelKey)`).

The real gap is coverage, not correctness. The migration stopped at the screen layer. Domain-generated text (`motivation.js`, `progression.js`) and seed data (`seedExercises.js`) still hold Spanish literals, and a handful of view literals slipped through (`'Cargando…'`, `'Ejercicio'` fallback, `'kg'`/`'reps'` units, the `'Mi rutina'`/`` `Día ${i}` `` default plan names). Since these are stored or displayed as-is, a future `en.js` will show Spanish in those spots. This is reasonable to defer for a Spanish-only release but should be tracked.

The banner localization runs before `setLocale`, so `setupInstallBanner`/`setupUpdateBanner` always render the default-locale text. Harmless with one language; produces a wrong-language banner once a non-default locale is selectable and set from a saved preference.

On iOS: the hardcoded `/hypro/icons/...` paths in `index.html` match the Vite `base: '/hypro/'` and the GitHub Pages subpath, so they are correct in production. They do not resolve under local `npm run dev`, which serves at root.

### Translation correctness: no broken keys

A scripted comparison of every `t('...')` call site in `src/` (excluding `src/i18n/`) against the keys defined in `es.js` found zero missing keys: 116 distinct keys are referenced statically and all exist. The five tab labels resolve through `labelKey` → `t(tab.labelKey)` and all five (`nav.train`, `nav.plan`, `nav.exercises`, `nav.progress`, `nav.settings`) exist. The only dynamic construction is the Settings language selector, `t(\`lang.${code}\`)`, and both `lang.es` and `lang.en` are present — so even a future `en` option renders its native name today. `common.confirm` is the sole defined-but-unreferenced key.

The `t()` fallback chain is the right shape for catching regressions: `(dict && dict[key]) ?? DICTS.es[key] ?? key`. A key missing from a non-default locale silently falls to Spanish; a key missing everywhere renders as its literal identifier, which is visible in the UI and asserted by a unit test (`t('no.existe.esta.clave')` → the key). Placeholder substitution leaves unmatched tokens as `{name}` rather than dropping them, which is also test-covered.

### resolveInitialLocale and stale saved locale

`resolveInitialLocale` gates every source through `supportedLocales`:

```js
const supported = APP.supportedLocales || ['es'];
if (saved && supported.includes(saved)) return saved;
const nav = (navigator.language || '').slice(0, 2);
if (supported.includes(nav)) return nav;
return APP.defaultLocale || 'es';
```

This directly answers the stale-locale concern: if a user previously saved `locale: 'en'` and a later build ships `supportedLocales: ['es']`, the saved value fails the `includes` check, browser language is tried next (also gated), and it falls to `'es'`. No crash, no raw keys. `setLocale` is independently defensive — it only switches if `DICTS[locale]` exists — so even a direct bad call can't leave `current` pointing at a missing dictionary. The `'fr' → 'es'` fallback is unit-tested.

### The `t` collision in main.js

The tabbar render loop changed from `TABS.map((t) => … t.label …)` to `TABS.map((tab) => … t(tab.labelKey) …)`, and the navigate lookup from `TABS.find((t) => t.id === tabId)` to `TABS.find((x) => x.id === tabId)`. Both loops previously shadowed the imported `t`; renaming the iteration variable restores access to the translation function exactly where the label is now resolved. No remaining shadow of `t` exists in the file.

### Banner localization ordering

In `main.js`, `setupInstallBanner()` and `setupUpdateBanner()` are called at module top level, before `boot()` runs `setLocale(...)`. Both functions localize their text eagerly at setup time:

```js
if (txt) txt.textContent = t('pwa.installText');
btn.textContent = t('pwa.install');
```

At that moment `current` is still `APP.defaultLocale`. With one locale this is invisible. With two, a user whose saved/browser locale is non-default sees the banners in the default language while the rest of the app is translated, because the banner text is set once at setup and never refreshed on locale change. The comment in the code ("el HTML trae los de español como fallback") shows the default-language coupling is understood; the ordering just needs to move after `setLocale`, or the banners need a re-localize hook tied to locale changes. The screens avoid this class of bug by calling `t()` at each render.

### Coverage gaps outside the screen layer

The migration is thorough within `src/ui/screens/` but three categories of text live elsewhere and were left in Spanish:

- **Motivation** (`motivation.js`): `DAILY` and `COMEBACK` are arrays of Spanish sentences returned directly to the UI as toast/notification bodies.
- **Progression** (`progression.js`): `suggestNext` returns `text` fields like `` `Hoy intenta ${reps} reps × ${lastBest.weight} kg` ``, rendered in Train as `💡 ${suggestion.text}`.
- **Seed data** (`seedExercises.js`): exercise names are Spanish. These are the thorniest case because they become stored, user-editable records, not display labels — internationalizing them is a data-model decision, not a `t()` swap.

Plus stray view literals: `'Cargando…'` (main.js), the `'Ejercicio'` name fallback and the PR line `` `${pr.repsAtBest} reps × ${pr.bestWeight}kg` `` (progressScreen.js), `'kg'`/`'reps'` unit spans (trainScreen.js), and the default plan/day names `'Mi rutina'` / `` `Día ${i}` `` (planScreen.js) that get persisted in Spanish.

None of these breaks the Spanish-only release. Each is a place where a second language would leak Spanish, so they belong on a tracked "i18n phase 2" list rather than being silently accepted.

### iOS install prep

`index.html` adds `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title`, and two `apple-touch-icon` links pointing at `/hypro/icons/icon-192.png` and `/hypro/icons/icon-512.png`. The absolute `/hypro/` prefix matches `vite.config.js` `base: '/hypro/'` and the GitHub Pages subpath `https://samosa13.github.io/hypro/`, so these resolve correctly in production. The manifest icons, by contrast, use base-relative paths (`icons/icon-192.png`) that Vite rewrites at build; the hand-written apple-touch-icon links bypass that rewrite and are hardcoded. The consequence is only that `npm run dev` (served at origin root) will 404 those icons — production is fine.
